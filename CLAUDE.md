# China EV DB — project reference

Single source of truth for this project's conventions, data model, and history — the
project used to split this across `BRAND_TAXONOMY.md`, `KNOWN_ISSUES.md`, and
`LISTING_CONVENTIONS.md`; those are now merged in here so there's one place to read,
not four. `AGENTS.md` above is auto-regenerated by `next dev` — don't hand-edit it.

## What this app is

A database of Chinese-market EVs/ICE/hybrids (`Brand` → `Model` → `Powertrain`
documents in MongoDB), cross-referenced against Morocco-market pricing/availability.
Next.js App Router + Mongoose. The homepage and brand pages default to showing only
models with a **confirmed Morocco price**, cheapest-first — see "Listing conventions"
below for why and where that's implemented.

Research (filling in specs, brand ownership, Morocco pricing) is AI-assisted: real web
search first (`lib/webSearch.ts`, Brave Search), then an LLM via Vercel AI Gateway
(`lib/aiProvider.ts`, DeepSeek by default) extracts facts ONLY from what was actually
fetched (`lib/groundedResearch.ts`). Every AI prompt in this codebase requires English
output — see "AI output language" below.

## Getting started

```bash
npm install
cp .env.example .env.local   # fill in MONGODB_URI, AI_GATEWAY_API_KEY, SEARCH_API_KEY

```

Useful scripts (`npm run <name>`, see `package.json` for the full list):
- `export-manual-research` / the model page's "Export for Kimi/DeepSeek" button —
  hand-carry a model's spec research through an external chat UI, then paste the
  response back in via the model page's import panel.
- `tech-spec-agent`, `morocco-agent`, `sync-prices`, `fetch-all-prices` — batch AI
  research passes (each writes a review file under `raw-data/`, or writes straight to
  Mongo with re-fetch verification — see each script's own header comment for which).
- `fill-missing-mandatory-fields` — backfills a small set of fields every Powertrain is
  required to have (`engine.displacement_l`/`torque_nm`, `motor.torque_nm`,
  `thermal_management`) wherever they're missing.

## AI output language

Every AI research prompt in this codebase requires the model to respond in English —
no Chinese (or other non-English) characters anywhere in the JSON response, even when
the source material is in Chinese (translate the fact before writing it). Two
deliberate exceptions, both called out explicitly in the prompts themselves:
- `name_cn` fields (Brand/Model) — these exist specifically to hold the original
  Chinese name.
- An *existing* `trim_name` in the manual DeepSeek/Kimi round-trip
  (`lib/manualResearchImport.ts`) — must be returned byte-for-byte unchanged (Chinese
  parentheticals included) or the import matches it as a new trim instead of updating
  the real one. A genuinely new trim being added should still be named in English.

Search queries sent to Brave Search stay in Chinese where useful (e.g. `"参数配置"`) —
that's an input needed to find Chinese-language sources, not model output.

## Data model conventions (Brand ownership/grouping)

- **`parent_group`** — the real controlling corporate parent only. Never a distributor,
  never a tech partner, never a compound string like `"Chery / JLR"`. A brand has
  exactly one `parent_group` (matching another brand's `name`) or none. Use
  `relationship_type` + `stake_percentage` (enum: `equity_subsidiary`, `jv_brand`,
  `technology_partner`, `minority_controlling`, `contract_manufactured`,
  `independent`) to capture ownership nuance instead.
- **`tech_partner`** — only a genuine, individually-sourced tech partnership (e.g.
  Huawei on AITO/Luxeed/Stelato/Maestro/Shangjie — the 5 real HIMA members). Never
  inherited from a sibling brand or the parent company. Yijing/Qijing have a real
  Huawei partnership too but are explicitly NOT HIMA — carry a distinguishing
  `status_note`.
- **`status_note`** is where ownership nuance that doesn't fit a single field goes
  (e.g. "Stellantis holds ~20% of Leapmotor") — never smuggle this into `parent_group`
  or `tech_partner` as a compound string.
- **Grouping UI** (`lib/brandGrouping.ts`) groups by `parent_group` only, walking the
  chain by matching against other brands' `name` field — match the *exact, full*
  parent string (e.g. `"GWM (Great Wall Motor)"`, not `"GWM"`). Never group by
  `tech_partner`; HIMA is not a brand and must never exist as a `Brand` document. A
  `parent_group` with only 1 sub-brand still gets its own named group.
- **Known-correct reference facts** (treat a future claim that contradicts these as
  something to verify, not apply blindly): Geely has no Renault ownership relationship
  (only the HORSE Powertrain JV + minority equity stakes, informational-only in
  `status_note`). Soueast/Exeed → parent `"Chery"`; Hongqi → parent `"FAW"`. AIVA →
  parent `"Chongqing Saidou Technology"` (not Seres). Jinguo → parent `"Juneyao
  Group"`. Cowin → parent `"Yibin State Capital"` (Chery holds an 18% minority stake).
  JMC → parent `"JMCG"` (Ford holds ~32% of listed Jiangling Motors Corp).
- **"Dongfeng Aeolus" was merged entirely into "Dongfeng"** (2026-09-13) — kept
  causing recurring duplicate-model bugs faster than upstream fixes could keep up, so
  the split was abandoned rather than chased further. Don't recreate it from a future
  research pass's own sub-brand claim without re-confirming with the user first. GAC
  Aion and Geely Galaxy remain separate, real sub-brands (not merged — large,
  well-populated, genuinely distinct); their duplicate model pairs were reconciled
  the same way without merging the brands themselves.
- Root cause of the Dongfeng duplication (fixed going forward): `resolveBrandName()`
  in `lib/deepseekNormalize.ts` resolved a brand from the current import entry alone,
  no cross-check against siblings. `scripts/import-deepseek.ts` now runs
  `preflightCheckCrossBrandDuplicates()` before any write, aborting the import if a
  model would collide with a same-parent sibling's existing model — general safety
  net for any future sub-brand split, not just Dongfeng.

## Listing conventions

Everywhere a list of brands or models is shown (homepage, a brand's model grid), the
default view:
1. **Filters to items with a confirmed Morocco price** (`morocco_price_confirmed ===
   true` and `morocco_price_dh` present) — an unpriced item is out of scope for the
   default view, not a first-class citizen. `morocco_price_dh` can be set without
   `morocco_price_confirmed: true` (e.g. an AI-fallback reconciliation pending human
   review) — only a confirmed price is trustworthy enough to show by default.
2. **Sorts cheapest-to-most-expensive** by that price — a brand's position is decided
   by its cheapest model, not alphabetically or by model count.
3. **Never hides data, only defers it** — every filtered-out item stays reachable via
   a `?all=1` query param, with a count of how many are hidden and why. Nothing is
   deleted from the database by this convention; it's presentation-only.

Implemented in `app/page.tsx` + `lib/brandGrouping.ts` (`getCheapestMoroccoPriceByBrandId()`,
`groupBrands()`, `Infinity` sentinel for unpriced) and `app/brands/[id]/page.tsx`
(same pattern for models within a brand). If a new page lists brands/models and should
follow this convention, reuse `getCheapestMoroccoPriceByBrandId()`'s query shape
rather than re-deriving it.

**Power always displays in hp, never bare kW** — `lib/units.ts`'s `kwToHp()`/`hpToKw()`.
Model detail + Compare page's table show both (`"150 kW (201 hp)"`); the trim picker
and search result cards (width-constrained) show hp-only; the spec-search power
filter inputs take hp and convert to kW client-side before hitting the API (the DB
itself stores/queries kW only). Reuse these two functions rather than hand-rolling
the conversion factor again.

**Two search surfaces, deliberately different axes**: `/search` filters `Model`
documents (brand, segment, production status, price); `/search/specs` ("Tech Search")
filters `Powertrain` documents (energy type, engine/motor power, battery, transmission
— results are individual trims, so one model can appear more than once), reusing
`compactSpecLabel()` from `lib/specGrouping.ts` for the same trim-summary format the
Compare page's trim picker uses. Both show an explicit "active filters" summary.
`app/api/powertrains/route.ts`'s `GET` refuses an entirely unfiltered request (400) —
every real caller always has at least one criterion.

**Compare page**: `?pmin=`/`?pmax=` in the URL is a single shared Morocco-price-range
filter applied to both sides at once, narrowing the model list before it reaches
either picker; a selection that falls outside a newly-narrowed range is cleared
automatically. Same "state lives in the URL" pattern as every other Compare control.

## Schema/prompt drift guard

`types/canonicalPowertrain.ts`'s `CANONICAL_POWERTRAIN_FIELD_TEMPLATE` is the single
source of truth for the Powertrain shape — the Mongoose schema
(`models/Powertrain.ts`), every research prompt, and response validation
(`lib/techSpecResearch.ts`'s `validateCanonicalVariant`) all derive from it. A
compile-time type check (`_CheckTopLevelKeys` etc. at the bottom of that file) fails
`tsc` if a field is renamed/added/removed on the interfaces without updating the
template — adding a new Powertrain field means updating both in the same change.

## AI free text needs a normalization layer before enum validation

A recurring pattern, hit three separate times in one evening (2026-09-15): an AI research
response reports a real fact correctly, but in free-text/descriptive form instead of the
exact enum token the schema requires — `battery.ev_range_standard` coming back as `"NEDC2"`
instead of `"NEDC"`; `thermal_management.has_liquid_cooling`/`has_heat_pump` arriving as
differently-named booleans (`active_liquid_cooling`/`heat_pump`) on one real Geely response;
`transmission.type` arriving as `"5MT manual"` / `"7-speed wet DCT"` instead of `"MT"`/`"DCT"`
on another. Prompt instructions and an embedded canonical-shape template (both already in
place for all three cases before they happened) are not sufficient on their own — an external
chat UI (the manual Kimi/DeepSeek round-trip) especially can't be relied on to follow them.

**When adding a new strict-enum field to the canonical Powertrain schema** (or auditing an
existing one), proactively ask: what free-text variants would a real AI response plausibly use
for this value, and does an alias/normalization function exist to resolve them before
`validateCanonicalVariant`/`validateManualPowertrain` runs? See `correctRangeStandard()` and
`correctGearboxType()` in `lib/deepseekNormalize.ts` for the established pattern: resolve a
known alias, and return `undefined` (never a guessed/passthrough value) when nothing matches —
the caller drops the field to `null` rather than either accepting an invalid enum value or
rejecting the whole record over one unresolved field. `lib/manualResearchImport.ts`'s
`KNOWN_FIELD_RELOCATIONS` table is the sibling mechanism for the same underlying problem one
level up — a field landing in the wrong shape/location entirely rather than the right location
with the wrong value.

(Known follow-up, not yet fixed: `lib/deepseekNormalize.ts`'s older `correctGearbox()` — used
by `scripts/import-deepseek.ts`, a separate pipeline — has its own `VALID_GEARBOX` list that's
missing `"E-CVT"`, added to the canonical enum after that list was written. Left alone when
`correctGearboxType()` was added rather than fixed as a drive-by, to avoid an unrelated
behavior change to a different, already-working pipeline.)

## Mandatory Powertrain fields

A small, explicitly-named set of fields is required (not just optional-but-common) on
every Powertrain record, enforced the same way at every ingestion path (Gemini-era —
now AI-Gateway — batch research, the manual DeepSeek/Kimi round-trip, and
`scripts/fill-missing-mandatory-fields.ts`'s backfill pass):
- `engine.displacement_l`, `engine.torque_nm` — required when `energy_type !== "BEV"`.
- `motor.torque_nm` — required when `energy_type !== "ICE"`.
- `thermal_management` (the whole block) — required when `energy_type !== "ICE"`; if
  genuinely unfound after searching, still return the block with
  `thermal_evidence: "UNKNOWN"` and `morocco_suitable: false` rather than omitting it.

## Write safety

Every AI-researched write path (`lib/applySpecUpdates.ts`, the manual-import apply
route) re-fetches and field-verifies after every write — a Mongoose call not throwing
does NOT mean the fields actually persisted. This exists because of a real incident: a
running dev server had an old cached Mongoose schema (pre-dating a new field), so
`$set` on that field was silently dropped under strict mode even though the write
"succeeded." A field added to a Mongoose schema needs a full process restart (dev
server, or a fresh serverless cold start in production) before writes to it persist.
